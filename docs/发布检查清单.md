# xserver 发布检查清单

本文档只服务一个目标：

- 在准备交付 production `xs` 时，用最短路径确认当前源码树仍然满足稳定基线



## 1. 先确认构建目标

- 发布版：`release/xs(.exe)`
- 调试版：`release/xsdbg(.exe)`

production 交付默认看 `xs`，`xsdbg` 只用于调试和排错。



## 2. 必跑检查

Windows：

```bash
cmd /c test_stable.bat
```

Linux：

```bash
sh ./test_stable.sh
```

这两个入口会先 build 当前源码，再执行稳定 smoke；它们是当前发布前最小必跑检查。

如果准备做扩展回归，建议再顺手跑：

- Windows：`cmd /c test_pressure.bat`
- Windows：`cmd /c test_soak.bat`
- Windows：`cmd /c test_memdebug.bat`
- Linux：`sh ./test_pressure.sh`
- Linux：`sh ./test_soak.sh`
- Linux：`sh ./test_memdebug.sh`



## 3. 发布通过标准

production `xs` 必须继续满足：

- 不再内置固定 `__xs/*` 管理应用
- `__xs/*` 路径已经回到应用层 Host 处理
- `/json` 业务路由可用
- `demo.callself`
- `demo.callrequeststatus`
- `ws echo`
- `custom echo`

当前稳定 smoke 还会用仓库 demo 额外确认：

- `GET /__xs/status_json`
- `HEAD /__xs/status_json`
- `POST /__xs/status_json`
- `GET /__xs/bus/status`
- `GET /__xs/dashboard`
- `GET /__xs/dashboard_json`

这些路径在 production `xs` 下已经由应用层处理，而不是命中框架内建管理面。

`xsdbg` 则必须继续保留当前内置调试应用，用于：

- 协议调试
- 错误排查
- 内存调试
- reload / check_config 诊断

但当前 xsdbg 内置调试应用已经不再承诺：

- `__xs/dashboard*`
- `__xs/bus/*`

发布前不再检查限流、治理看板、在线策略编辑、异步 XTP pending request 或持久 XTP client 对象体系；这些不是当前 production `xs` 的交付阻塞项。



## 4. 人工抽查

如果准备正式交付，建议顺手再看两件事：

- 从仓库根目录启动 `release/xs(.exe) xs_manage_test.json`，确认 `GET /__xs/status_json`、`GET /__xs/dashboard`、`GET /__xs/bus/status` 返回的是应用层文本响应，而不是框架内建管理页
- 从同一配置启动 `release/xsdbg(.exe) xs_manage_test.json`，确认 `GET /__xs/status_json`、`GET /__xs/http_metrics_json` 仍能命中内置调试应用，而 `GET /__xs/dashboard` 继续走应用层
