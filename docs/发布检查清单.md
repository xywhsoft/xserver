# xserver 发布检查清单

本文档只服务一个目标：

- 在准备交付 production `xs` 时，用最短路径确认当前源码树仍然满足稳定基线



## 1. 先确认构建目标

- 发布版：`release/xs(.exe)`
- 调试版：`release/xsdbg(.exe)`

production 交付默认看 `xs`，`xsdbg` 只用于调试、治理和重观测面验证。



## 2. 必跑检查

Windows：

```bash
cmd /c test_stable.bat
```

Linux：

```bash
sh ./test_stable.sh
```

这两个入口会先 build 当前源码，再执行稳定 smoke；它们是当前发布前最小必跑检查。
并且现在会自动验证：

- 跑完后没有残留 `xs / xsdbg` 进程
- 两份被跟踪的 `xrt_mem_report_auto.json` 没有被改写
- smoke helper 产物已经清理干净



## 3. 发布通过标准

production `xs` 必须继续满足：

- `status / status_json = 200`
- `health / health_json = 200`
- `reload / reload_json / reload_config / reload_config_json / reload_status / reload_status_json = 200`
- `check_config / check_config_json = 200`
- `/json` 业务路由可用
- `demo.callself`
- `demo.callrequeststatus`
- `ws echo`
- `custom echo`

同时，production `xs` 还必须继续保持：

- `dashboard* = 403`
- `__xs/bus/* = 403`
- `*_metrics* = 403`
- `reload_clear / reload_reset / check_config_clear = 403`

`xsdbg` 则必须继续保留上面这组扩展调试面。



## 4. 人工抽查

如果准备正式交付，建议顺手再看两件事：

- 从仓库根目录启动 `release/xs(.exe) xs_manage_test.json` 仍然可用
- 首页在 production `xs` 下会自动降级，不把 `dashboard / bus / *_metrics* / clear-reset` 暴露成可点击的调试入口

补充说明：

- `test_stable.*` 现在已经自动验证没有残留 `xs / xsdbg` 进程；只有在 smoke 中途异常中断时，才需要手工再查一次进程残留



## 5. 相关文档

- 稳定 API：`docs/稳定API.md`
- legacy 对照：`docs/legacy对照.md`
- 运行补记：`docs/运行与稳定补记.md`
- 验证入口：`test_stable.bat`、`test_stable.sh`

如果未来要新增任何内建 `__xs/*` 入口，默认应先进 `xsdbg`；只有在更新上述文档并同步更新 `test_stable.*` 后，才允许进入 production `xs`。

## 6. 首页直链审查

- 首页里 xsdbg-only 的 `dashboard / *_metrics* / reload_reset / check_config_clear` 直链，要继续挂在 `data-debug-manage="true"` 下
- 首页里的 `bus/status` 直链，要继续挂在 `data-bus-manage="true"` 下
- 目标是避免 production `xs` 首页重新出现新的可点击 `403` 调试入口；这一项属于人工抽查的静态补充
