# xs 路由系统跨语言性能基准报告

- 日期：2026-09-04
- 基准设施：`tools/routebench/`（语料生成、C 负载客户端、五方服务、总跑批器）
- 原始数据：`tools/routebench/results.json`

## 1. 测量目标与方法

测量**应用层路由系统**的每请求处理时延：从"服务器已启动并预热完成"起表，到最后一条请求的响应末字节收完停表。

- **语料**：每档 N 条路由 = N/2 静态精确（`/s/resNNNNNN/detail`）+ N/2 动态参数（`/d/resNNNNNN/{id}`），请求路径在全部 N 条上均匀轮转，静态/动态各占 50%；
- **档位**：N = 10 / 100 / 1,000 / 10,000；
- **次数**：每档每服务 3 轮 × **10,000 请求**，取三轮中位数（报告同时给出轮间波动）；
- **客户端**：统一 C 编写的 `loadgen.exe`（Winsock，单连接 keep-alive 顺序请求），对全部被测服务完全一致——绝对值含客户端与本机回环成本（估算 10~20µs），差值比较有效；
- **响应**：所有服务统一返回常量 `200 text/plain "ok"`，仅路由结构不同；
- **连接语义**：PHP 内建服务器每响应关闭连接且不声明 `Connection: close`，客户端按"读失败即重连重发"处理，**重连成本计入 PHP**（属其真实每请求行为）；
- 环境噪声控制：被测服务与客户端同机独占运行，跑批器串行调度。

## 4. 解读

**第一梯队（C 级，平坦）：Node / Go / xs，28~59µs。**

- **Node 最快且最平**（33~35µs，10k 条不增反微降）：V8 JIT 让路由代码（Map.has、末段键切片查表）达到原生机器码级；原生 http 栈（llhttp C 解析器 + 单次缓冲写 + 年轻代指针碰撞分配）每请求固定成本极低，且无框架层。注意这是**手写两级路由**的结果——Express 等逐层匹配框架是另一回事（见 FastAPI 形态）。Node 轮间波动较大（GC/事件循环节奏），中位数跨档稳定。
- **Go 与 xs 同档**（42~46 vs 43~59µs）：N≤100 时两者不可区分；N≥1,000 后 xs 慢约 12µs。来源有三：xrtPattern 动态匹配走哈希分派状态机（Go 1.22 mux 同样如此，差距不大）；xs 引擎对每个请求做完整的 HTTP/1 解析 + Header pin（为借用视图安全付出的拷贝）；脚本侧 RouteInfoHTTP 经 TCC 间接调用。**12µs 的差额占请求预算 2%~0.03%（随端点业务量增大而稀释）**，对范例与典型应用都不构成取舍依据。
- 三者的共同点：**路由耗时与路由数量基本无关**（10→10,000 条，Node −1.5µs、Go +4.1µs、xs +16.2µs），哈希/树形结构的 O(1)/O(路径长度) 特性在真实端到端路径上成立。

**第二梯队（线性增长）：PHP 390→2,300µs、FastAPI 380→3,749µs。**

- 两者 N=10 时与 C 级差约 10 倍（解释器每请求固定成本），且**随路由数线性恶化**（10k 条时分别为 C 级的 40~78 倍）——这是"逐条匹配 + 每请求重建路由结构"的形态税：
  - PHP：`php -S` 每请求重执行路由脚本（opcache 省了解析，数组仍要重建 N 项）+ 每请求关闭连接（重连计入）；N=10k 时数组重建主导。
  - FastAPI/Starlette：注册表按序逐条匹配，命中期望位置随 N 线性后退；Python 每请求成本叠加。
- 对比早前微基准（同机）：FastAPI 的路由层在纯匹配语境约 4µs/条（Python re）——端到端 10k 条 3.7ms 与"逐条线性 + 每请求解释器开销"的模型自洽。

**结论**：xs 的"静态 xrtMap + 方法槽位 + xrtPattern 动态表"分层在端到端测量中达到了 C 级性能（与 Go stdlib 同档、落后 Node 极简路径约 1.3~1.7 倍），并保持与路由数量近无关的平坦性；其 10k 档 +16µs 的增量主要是引擎解析严格性与 TCC 间接层的固定成本，不随业务复杂度放大。

### 勘误记录（2026-09-04）

首轮数据中 Node 行曾为 28µs——系语料文件 CRLF 行尾使 Node 路由解析正则全部失配，**服务全程返回 404 空体**（无路由工作）所致；同批 Go（TrimSpace）与 FastAPI（strip）不受影响。修正：语料改 LF 行尾、Node 解析加 trim、动态路由改为"末段参数前缀"Map 键（O(1)，与 xs 语义同构），Node 全档复测为 33~35µs。此事例已作为基准纪律记入：**每方服务必须先做命中正确性抽检再计时**（当前 run_bench 已含预热读校验，后续应升级为显式 200 断言）。

## 5. 局限与复现

- 绝对值含统一客户端与回环成本，仅差值与增长率可比；
- 单连接顺序请求测**每请求时延**，非并发容量（此前多连接压测 xs HTTP ≈ 11k RPS 时含真实业务处理）；
- PHP 采用内建服务器（每请求关连接 + 重执行脚本），FPM/Swoole 常驻形态会显著改善其 N=10 档绝对值，但"每请求重建路由结构"的线性增长形态不变；
- FastAPI 为官方推荐部署（uvicorn 单 worker）；Node 为无框架原生实现——两者分别代表"典型框架注册表"与"手写最优"两个参考点，不是同一抽象层。

复现：

```bash
python tools/routebench/gen_corpus.py 10,100,1000,10000 tools/routebench/corpus
gcc -O2 tools/routebench/loadgen.c -o tools/routebench/loadgen.exe -lws2_32
python tools/routebench/run_bench.py        # 约 20 分钟，输出 results.json
```

服务实现：xs（`release/routebench/`，复用 demo-single 的 `modules/protocol.h`）、Go/Node/PHP/FastAPI（`tools/routebench/servers/`）。
