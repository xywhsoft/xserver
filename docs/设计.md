# xs3 设计定稿

> 状态：定稿（2026-08-29）
> 性质：本文件是 xs3 的奠基设计文档，所有实现以此为准；与它冲突的历史实现（xhs / xserver）仅作参考。
> 证据基础：本文档中的关键论断均经过代码核实或 PoC 验证，见[附录 A](#附录-a验证事实)。

## 1. 定位与设计哲学

**xs 本质上是一个 xrt 的落地化包装程序。xrt 才是主要的那个，xs 的定位永久为：基于 xrt、面向应用部署的典型应用程序。**

由此推出的全部设计原则：

1. **能力归 xrt，部署归 xs。** 协议编解码、连接运行时、TLS、流控、限额、定时器原语、value/JSON/容器/模板/压缩——全部由 xrt 提供。xs 只做配置、装配、生命周期和脚本宿主。如果发现 xs 需要某个"功能"，第一反应应该是"这该进 xrt"，而不是在 xs 里加代码。
2. **xs 不教你怎么做事。** xs 传给回调的是 xrt 原生对象；应用决定用多底层的能力——是直接操作传输层，还是（未来）在更上层盖自己的东西。未来 xhttp 压实后接入，xs 也不会强制使用它。
3. **不做限制。** C 语言无法被沙盒约束，因此不做任何权限、命名空间、访问限制。一个 server 的 host 可以直接访问另一个 server 的 host 配置，可以直接重载另一个 host——全部允许。
4. **约束属于上层应用。** 要治理、要规矩，由 xadmin 这类上层应用自己实现。xs 只提供无限制的扩展能力和底层。
5. **一切为应用开发便利让步。** 配置文件是应用的一部分；协议旋钮与应用自定义字段同住一份 JSON；结构体直读而非层层包装。

## 2. 背景与动机（为什么推倒重做）

演化史（均有代码考证）：

```
xhs（mongoose 全家桶，宿主 ~2.6k 行）
 └─ xserver 首版（mongoose，main.c 549 行）
     └─ 去 mongoose，旧 xrt 接管网络（httpd/ws 在旧 xrt 内核）
         └─ 基于旧 xrt 全面重构（xs 自有代码 3,383 行，bus 诞生）
             └─ 5 个月膨胀至 30,513 行：
                bus 3,398 | xtp 3,639 | manage 层 ~10.6k | xs* 包装层 3,304
                | reload 差异化重建 | 1,338 个符号的脚本导入面
```

膨胀部分没有真正发挥作用（生产应用 xadmin 对 bus 仅 6 个调用点、对 XTP 仅 6 个临时测试调用点），却显著拖慢了演进。**xs3 = 回到初版的体量与心智模型（薄宿主），但在新版 xrt 之上，且带着这五年沉淀的正确机制。**

## 3. 总体架构

### 3.1 代码结构（目标体量 ~4–7k 行）

```
xs3/
├── main.c                  启动、信号、优雅停机（引擎常驻，无自建事件循环）
├── src/
│   ├── core/               xs.json 解析、XS_ServerInfo/XS_HostInfo、引擎与监听器装配
│   ├── protocol/
│   │   ├── http.c          ~2k 行：连接驱动（keep-alive/三态返回）+ 静态文件层
│   │   ├── ws.c            ~400 行：升级移交 + xrtWsStreamAttach + shim 分发
│   │   ├── stream.c        ~300 行：tcp/custom 共用（裸流事件透传）
│   │   └── udp.c           ~200 行：UDP 事件透传
│   ├── runtime/            generation 运行时、连接注册表、软重载时序、
│   │                       ServiceSwap 交接、TLS 证书表与热替换
│   ├── script/             TCC 宿主、分组符号导入、可选库宏门控
│   └── sdk/                xsbase.h（契约头，经 VFS 内置于二进制，不落盘）
├── lib/                    xrt 单头（锁定版本）、可选扩展库源码
├── tcc/                    TCC 编译器源码（0.9.28rc：libtcc + VFS + UTF-8 IO + LZMA 解码）
├── res/                    VFS 构建目录（res/tcc = 内置 TCC 环境，构建期打包进二进制）
├── release/                xs.json 范例、wwwroot、示例脚本（无 TCC 环境，单文件交付）
├── docs/
├── build.bat / build.sh
```

### 3.2 运行时拓扑

- **一个进程，一个常驻 xrt 网络引擎**（worker 数可配）。软重载永不重启引擎；引擎 Stop/Destroy 仅发生在进程退出且全部连接排空后。
- 每个 `XS_ServerInfo` 持有自己的 listener（普通/TLS）；`custom` 类不建 listener，应用从 `Server->Engine` 出发全手动。
- 回调在 xrt worker 线程上按流串行执行；xs 没有自己的线程模型。

## 4. 数据模型：server + host 两层

五种协议类统一为两层结构，无特例：

| 协议类 | host 的语义 |
|---|---|
| http / https | 传统虚拟主机：按 Host 头 / SNI 在 DefaultHost + Hosts 间路由 |
| ws / wss | 同 http（握手时按 Host 路由） |
| tcp | server 单层使用；允许配 hosts，**语义由应用自定**（如首行协议分流），回调挂 DefaultHost |
| udp | 同 tcp |
| custom | server 与 host 全由用户决定，xs 不装配，仅提供数据结构 |

**恒有 DefaultHost**：未配置 hosts 时由服务级 `devlang/devfile` 合成默认主机。这一条消除了 tcp/udp 的特殊分支——回调统一挂 DefaultHost，http/ws 在多主机间路由。

### 4.1 结构体定义（ABI 契约，随 xsbase.h 发布）

```c
typedef struct {
    /* ---- 身份与开关 ---- */
    bool            Enabled;
    const char*     Class;      /* "http"|"ws"|"tcp"|"udp"|"custom" */
    const char*     Name;       /* 唯一名，xsServerFind 的键 */
    /* ---- 监听 ---- */
    const char*     IP;
    uint16_t        Port;
    bool            TLS;
    uint16_t        PortTLS;
    const char*     IPTLS;      /* 缺省复用 IP */
    /* ---- 保护参数（直通 xrt 监听配置）---- */
    uint32_t        Backlog;
    size_t          RecvLimit;
    /* ---- Hosts ---- */
    XS_HostInfo*    DefaultHost;    /* 恒存在 */
    uint32_t        HostCount;
    XS_HostInfo**   Hosts;
    /* ---- 运行态（xs 维护，非配置）---- */
    XS_RunState     State;      /* 发布时固化的 starting/running/stopped 快照 */
    void*           Runtime;    /* 当前代脚本运行时（不透明） */
    struct xnetengine* Engine;  /* 进程级引擎（custom 类的起点） */
    /* ---- 应用领地 ---- */
    xvalue*         Custom;     /* 非预设字段全入此处 */
} XS_ServerInfo;

typedef struct {
    bool            Enabled;
    const char*     Name;
    const char*     Host;       /* 域名绑定（分号分隔）；http/ws 用于路由，
                                   tcp/udp/custom 语义由应用自定 */
    const char*     Path;       /* 资源/脚本根 */
    const char*     DevLang;
    const char*     DevFile;
    const char*     TlsCA;      /* host 级证书 = SNI 选择器数据源 */
    const char*     TlsCert;
    const char*     TlsKey;
    XS_RunState     State;
    void*           Runtime;
    XS_ServerInfo*  Server;     /* 反向指针：从一个 host 摸到整个拓扑 */
    xvalue*         Custom;
    /* 尾部追加（ABI 纪律：只增不改） */
    const char*     DevInc;     /* 脚本额外头目录（分号分隔，相对 appPath，见 §11.6） */
    const char*     DevLib;     /* 脚本额外库目录（同上） */
} XS_HostInfo;
```

设计纪律：

- **只留装配必需字段。** `desc / param` 一类"给应用看的"字段不进结构体——`param` 的职责由 `Custom` 承接。
- **协议驱动旋钮也住在 Custom**（见 §5.3），结构体与协议无关。
- **ABI 演化策略**：布局冻结；新字段只许尾追加、永不重排改名；宿主与脚本永远用随二进制同发的 `inc_xs/xsbase.h` 编译（初版 xs 验证过的模式）。Custom 吸收绝大多数演进需求，使结构体变更降到极低频。

### 4.2 生命周期归属

配置结构体、其字符串、其 Custom xvalue，由 generation 引用的不可变 **ConfigRevision** 持有；一次 reload-all 的多个新 generation 共享同一 revision，最后一个引用终态才释放整棵树。旧代上的在途请求持有旧代指针，安全到排空。`xsServerFind` 返回当前代的 retained lease，必须 `xsServerRelease`；枚举回调参数只在回调内借用，跨回调保存前必须 `xsServerRetain`。host 指针由其 server lease 共同保护。拓扑换槽、数组扩容与查找/枚举由进程级 RWLock 线性化，不再存在无所有权裸指针窗口。`State` 在发布后不再跨线程改写；reload 成败只通过 ticket 查询，避免把运行中旧代误标为失败并产生普通数据竞争。

## 5. 配置文件（xs.json）

### 5.1 形态

```json
{
    "engine": { "workers": 4 },
    "services": [
        {
            "enabled": true, "class": "http", "name": "main",
            "ip": "0.0.0.0", "port": 80,
            "backlog": 128, "recv_limit": 1048576,
            "host_default": {
                "name": "app", "path": "wwwroot",
                "devlang": "c", "devfile": "script/main.c",
                "dev_inc": "devsdk/inc", "dev_lib": "devsdk/lib"
            },
            "hosts": [
                {
                    "name": "admin", "host": "admin.example.com",
                    "path": "hosts/admin/wwwroot", "devfile": "hosts/admin/main.c",
                    "cache_ttl_ms": 30000,
                    "feature_flags": { "jwt": true }
                }
            ],
            "body_limit": 262144,
            "security_gateway": { "rate_limit": 100 }
        }
    ],
    "xadmin_global": { "theme": "dark" }
}
```

字段命名沿用现行 snake_case（`port_tls / host_default / hosts`），使既有 xs.json 平滑迁移。

### 5.2 解析规则

- 仅有的结构约定：顶层 `services` 必须是数组；服务对象内 `host_default / hosts` 为结构键。
- **预设字段弹出进结构体**（大小写按 xs 定义）；对象剩余部分整体 move 为该 server/host 的 `Custom`（零深拷贝）。
- 顶层除 `services` 外的一切 → 根 Custom，经 `xsConfigRoot()` 访问。
- `engine` 为根级文档化旋钮（workers 等），由 xs 装配引擎时读取。

### 5.3 协议驱动旋钮（住在 Custom，文档化键名）

| 键 | 消费者 | 缺省 |
|---|---|---|
| `engine.workers` | 引擎装配 | xrt 默认 |
| `body_limit` / `header_limit` / `path_limit` / `idle_timeout` | http 驱动 | `body_limit=0` 取 `recv_limit`（默认 1 MiB）；其余取各自默认 |
| `ws_message_limit` / `ws_protocol` / `idle_timeout` | ws 驱动 | websocket core 默认 |
| `idle_timeout` | tcp/tcps 驱动（连接注册表扫描，毫秒） | 关闭 |
| `dev_inc` / `dev_lib`（**host 预设字段**，服务级折叠进 DefaultHost） | TCC 宿主：脚本额外 头/库 目录（分号分隔，相对 appPath；缺失目录静默跳过；详见 §11.6） | 无 |
| `static.index` / `static.headers` / `static.error_pages` / `static.deny_dotfiles` | 静态层（host Custom） | 见 §8 |

驱动旋钮与应用自定义字段同 namespace：**配置文件真正成为应用的一部分**，xs 只是一并解析了它认识的那几个键。键名冲突由应用自管。

### 5.4 校验姿态

- 结构必需项 fail-fast：`services` 非数组、`class` 非五类之一、预设字段类型不符 → 启动/重载报错并指名字段，整次解析作废。
- host `name` 在 server generation 内唯一；启用的次级 HTTP/WS host 必须配 `host`。`host` 是分号分隔的精确 authority 名（不带端口），装配时统一解析，空项、非法项或跨 host 重复均拒绝。
- Custom 内容照单全收，任何 JSON 形状合法；语义校验是应用的事。

## 6. 协议入口与回调契约

**核心原则：xs 只透传 xrt 原生对象，不包装。** 回调收到的东西，必须既能用 xrt http core 直接消费，也能被未来的 xhttp 在同一 substrate 上消费。

### 6.1 HTTP（http / https）

```c
typedef struct {
    xnetstream*         tcp;    /* 与 tls 二选一非空：传输层裸指针 */
    xtlsstream*         tls;    /*   可直接使用 xrt 全套流/发送 API */
    const xhttp1head*   head;   /* 解析产物：MethodCode 枚举 + 原始方法/目标/字段视图 */
    xhttp1body*         body;   /* 分帧状态机：定长/chunked/关闭三态 */
    const XS_HostInfo*  host;
    XS_ServerInfo*      server;
} XS_HttpReq;                   /* 视图结构体：一组 xrt 指针 + 归属，非对象系统 */

#define XS_OK        0   /* 已完成响应（已写出状态行+头+按分帧的完整 body），
                             驱动消费 body 余量后继续 keep-alive */
#define XS_FALLBACK  1   /* 未处理：GET/HEAD 落入静态层，其余 404 */
#define XS_TAKEOVER  2   /* 应用可自行收发并最终 Close；不得替换事件表，
                             Close 终态由 xs Destroy 并释放 generation lease */

typedef int XS_RequestResult;
XS_RequestResult RequestProc(XS_HttpReq* req);
```

- 常用方法直接比较 `head->MethodCode`（`XHTTP_METHOD_GET`、`XHTTP_METHOD_POST` 等）；`XHTTP_METHOD_OTHER` 表示合法扩展方法，应用仍可读取 `head->Method` 原始视图继续分派。
- 响应由应用用 `xrtHttp1ResponseWrite / xrtHttp1Chunk*Write` + `xrtNetStreamSend*` 自己构造——**xs 不提供任何 HTTP 应答便利函数**（上层应用如 xadmin 自建 reply 层）。
- 连接只固定 Accept 时的 server generation；每个请求都在该 generation 的不可变虚拟主机表中重新路由，因此同一 keep-alive 连接可以先后访问不同 host。命中 host 同时决定 `RequestProc`、`Path`、`static.*` 头/首页/错误页。
- HTTP/1.1 的 Host 必须唯一且合法；Host 名忽略 ASCII 大小写并忽略请求端口。origin-form 按 Host 路由，absolute-form/CONNECT 按 request-target authority 路由；未命中时回落已启用 DefaultHost，无回落则 404。
- `header_limit` 是接收完整请求头的线路硬边界，填满仍不完整返回 431；`body_limit` 同时约束定长和 chunked 解码后的累计 body，超限返回 413，协议畸形返回 400。chunked 使用独立增量 reader 探针，避免反复从头扫描。
- 静态文件只通过装配期已打开的 host 根目录句柄按相对段解析；根目录打不开会让该候选启动/重载失败。拒绝绝对路径、反斜杠、NUL、`..` 及逃逸根目录的符号链接。文件按发送预算异步分块续传，声明的 `Content-Length` 与传输队列全部排空前不解析下一条 pipeline 请求；响应头写出或文件发送失败后立即关闭连接，不再尝试复用半响应流。
- `XS_TAKEOVER` 的流仍属于原 generation：应用可跨线程收发并最终 `Close`，但不得替换 xs 安装的终态事件表。接管后 xs 把 `Read` 置空，应用通过 TCP/TLS pull/Future API 接收后续字节；xs 在 `Close` 回调中 `Destroy` 并释放 lease。无法遵守这一边界的裸资源应使用 custom，且 custom 不支持在线卸载。
- HEAD、100-continue 等语义由应用按 core 能力处理。

### 6.2 WebSocket（ws / wss）

xs 完成握手（`xrtWsUpgradeRequestCheck` → 101 → `xrtWsStreamAttach`），回调收 `xwsstream*`：

```c
void WsOpen(XS_HostInfo* host, xwsstream* ws);
void WsText(XS_HostInfo* host, xwsstream* ws, xstrview text);
void WsBinary(XS_HostInfo* host, xwsstream* ws, xbytesview data);
void WsPing(XS_HostInfo* host, xwsstream* ws, xbytesview data);   /* 可选导出 */
void WsPong(XS_HostInfo* host, xwsstream* ws, xbytesview data);   /* 可选导出 */
void WsClose(XS_HostInfo* host, xwsstream* ws, uint16 code, xstrview reason);
```

升级检查通过后、101 发送前按同一虚拟主机表路由。命中的 host 和脚本 runtime 在整条 WS 连接上固定，后续帧不再查全局拓扑。每个启用的 WS host 都必须有脚本并导出 `WsText` 或 `WsBinary`。子协议协商旋钮 `ws_protocol` 在 server Custom。

### 6.3 TCP / TCP+TLS（tcps）

tcp 类：xs 建监听（含 tcps 形态：host 证书 → SNI 身份表），流事件透传脚本。
回调收到 XS_StreamConn 视图（tcp 与 tls 二选一非空，与 XS_HttpReq 同构）：

```c
typedef struct XS_StreamConn {
    xnetstream* tcp;    /* 明文形态 */
    xtlsstream* tls;    /* tcps 形态：发送走 xrtTlsStreamSend，消费走 xrtTlsStreamConsume */
} XS_StreamConn;

void EventOpen(XS_HostInfo* host, XS_StreamConn* conn);
void EventData(XS_HostInfo* host, XS_StreamConn* conn, xnetbuf* buf);  /* tcps 下 buf 仅供 Peek */
void EventClose(XS_HostInfo* host, XS_StreamConn* conn, xnetresult result, const xerror* err);
```

- **连接生命周期由 xs 持有**（Accept 接管 → 连接注册表 → Close 时 Destroy），应用不负责 Destroy——与 custom 类"一切手动"不同；
- 注册表同时提供 idle 超时保护（server Custom 旋钮 `idle_timeout` 毫秒，缺省关闭）与停机批量收口，是后续热重载按代 drain 的同一套基础设施；
- SNI：ClientHello ServerName 使用与 HTTP/WS 相同的 authority 名规则（分号分隔、忽略 ASCII 大小写），跳过禁用 host，无匹配回落首个可用身份；
- 证书链/密钥算法（RSA、P-256、P-384）自动识别，路径相对 appPath 解析（UTF-8）。

custom 类：xs 不建监听，契约即 §6.1 之前的"引擎交出 + 一切手动"（应用用原生 xnetstreamevents 自建，示例 release/script/custom_main.c）。

```c
/* 部署信息与嵌套编译 */
const char* xsAppPath(void);                       /* xs 可执行文件所在目录 */
TCCState*   xsCreateTCC(void);                     /* 预置标准 include/lib 路径
                                                    * （基础 VFS 环境，不含 host 的 dev_inc/dev_lib） */
void        xsDestroyTCC(TCCState*);
xvalue*     xsSwapTake(XS_HostInfo* host);          /* 重载交接：仅新代 ServiceInit 内有效 */
```

其余一切能力（含 HTTP 读写、value、JSON、并发、文件、模板、压缩、sqlite……）皆为 xrt 或可选库符号，脚本直接调用。脚本编译环境的额外目录经配置注入（`dev_inc` / `dev_lib`，见 §11.6），不占 API 名额。

## 8. 静态文件层（xs 提供的仅有"HTTP 功能"）

职责四件事，其余交给 `xrtNetStreamSendFile`：

1. **过滤**：路径规范化、`..` 穿越、点文件、反斜杠拒绝；
2. **映射**：MIME 推断 + 自定义响应头（host Custom 的 `static.headers`）；
3. **错误页**：404/403/50X 内置极简页，`static.error_pages` 可覆盖为应用页面；
4. **索引**：目录请求按 `static.index`（默认 `index.html`）回落。

static 四旋钮实现形态（全部 host Custom 的 `static` 对象，装配期消费）：

| 旋钮 | 形态 | 性能设计 |
|---|---|---|
| `static.headers` | `{ "X-Name": "value", ... }` 逐条配置 | **装配期一次遍历渲染**进每 host 缓存（blob + 就绪字段视图）；请求路径仅 `memcpy` 字段数组，零字符串处理。禁止覆盖 `Content-Length`、`Content-Type`、`Transfer-Encoding`、`Connection` 等 framing/hop-by-hop 字段 |
| `static.error_pages` | `{ "404": "err404.html", ... }` | 键必须是 `400..599`；错误路径按需打开文件并走同一有界异步发送器，未配置走内置极简页 |
| `static.index` | `["index.html", "home.htm"]` 数组逐个回落 | 目录请求按序尝试，首中即止；缺省 `["index.html"]` |
| `static.deny_dotfiles` | `true/false`（缺省 true） | 点文件开关；`..` 穿越与反斜杠**恒拒**不受此旋钮影响 |

范围剪裁：不做 Range / ETag / 预压缩——那是 xhttp 的地盘。

## 9. 并发模型

xs 没有自己的线程模型，声明如下：

- 回调在 xrt 引擎 worker 线程按流串行执行；**阻塞回调会占住所在 worker——这是开发者的选择，不是 xs 的错误**。
- 发送 API 可能因对端 RST 在当前调用栈同步进入唯一 Close 终态。HTTP/TCP/WS shim 在每个可重入回调外围同时持有连接记录和具体 stream 的临时引用；Close 立即摘表并撤销连接所有权，记录、脚本、generation 与 stream 的最终释放则由最后一个回调引用完成。这样终态不被延迟或泄漏，当前回调也不会踩到已经释放的对象。
- 重活投递到 xrt task/executor 或自开线程；HTTP 侧以 `XS_TAKEOVER` 衔接（引用计数跨线程）。
- 协程、future、channel、cancel 符号全部导出；用好是用应用的事。
- 定时器经 `xsTimerAfter` 注册即绑定 generation，换代自动作废。

## 10. 热重载（软重载）

### 10.1 模型：期望状态协调器 + generation

- reload 不是 FIFO 命令队列，而是“把目标收敛到最新期望版本”。独立 controller 线程负责读取、编译、初始化和绑定，不占用网络 worker。
- host/server intent 的真实发布单元都是完整 server generation；同 server 只保留最新 intent，all intent 覆盖全部尚未进入 staging 的 intent。编译、校验、端点预绑定完成后 intent 越过 staging 线性点，再来的期望状态排在它后面，不能取消已经开始产生应用副作用的 `ServiceSwap/ServiceInit`。
- 每次成功发布产生新 generation。旧代立即停止新接入，但继续服务 Accept 时已经捕获的旧连接；最后一个脚本活动归还后由 reaper 执行 `ServiceUnit`，最后一个总引用归还后仍由 reaper 释放 driver、TCC 和配置 revision，网络终态回调只记账和投递。
- 不设宽限期，不设超时强制释放，不用泄漏换取无 UAF。连接、listener、socket、timer 和公开 topology lease 都必须通过自己的唯一终态准确 Release。

### 10.2 时序（以 server/all 重载为例）

```
1. Submit 只记录目标名称并返回 reload_id；与当前 active/pending intent 做 latest-wins 合并
2. controller 冻结本次 xs.json 字节并只解析一次；reload-all 的全部新 server 共享这一份不可变 ConfigRevision
3. 先编译目标 server 的完整脚本集合：HTTP/WS 包含所有启用 host（HTTP 允许纯静态 host，WS 不允许无处理脚本），其他协议为 DefaultHost；任一编译/导出校验失败则整个候选作废，旧代不动
4. 端点改变：候选 listener 可先 bind，但 listener slot 保持 not-accepting
   同端点且固化参数不变：候选不重复 bind，预检旧稳定 listener slot 可交接
5. 所有可失败的编译、配置/TLS 校验和 endpoint 预绑定完成，再对全部 listener slot 做一次无副作用预检后越过 staging；此前若已被新 intent 覆盖，候选全量回收
6. staging 后旧代 `ServiceSwap` 以**无破坏快照**导出状态，候选 `ServiceInit` 消费；旧代在正式发布前仍必须可继续服务。候选脚本保持 not-ready，Init 创建的 timer 被 generation 发布屏障阻挡。Init 获得的资源必须归候选所有，异常提交失败由该候选的 `ServiceUnit` 对称回收
7. 持有同一 topology 写锁：交接/激活新 listener slot → 封住不再复用的旧 slot
   → 整体替换 server 数组与 Root → 将全部候选脚本置 ready → 解锁
8. 所有 Accept 先取 topology 读锁，因此只能观察到完整旧 revision 或完整新 revision，不会看到 reload-all 半新半旧
9. 解锁后对旧 driver 发出 Stop/retire；已有连接继续持有旧 generation，归零时自动终态析构
```

`class/tls/ip_tls/port_tls/backlog/recv_limit` 等 listener 创建时固化的字段若在同一端点改变，不能无损交接，必须明确拒绝并保持旧代；变更端点则走“先 bind 但不接入”的候选路径。

### 10.3 支撑机制

| 机制 | 设计 |
|---|---|
| generation lease | 初始管理引用为 1；listener、connection、UDP socket、idle/lifecycle timer 与公开 server lease 各持引用，只能在各自唯一终态释放。退役代的最后一个脚本活动结束后向 reaper 投递一次 ServiceUnit，使脚本可以释放跨 server lease；最后一个总引用归零后再向同一 reaper 投递 driver/TCC/配置终析构，网络线程不执行这些重活 |
| 拓扑 lease | `xsServerFind/Retain` 在拓扑读锁内增加 generation 引用，`xsServerRelease` 精确撤销；枚举先构造 retained 快照。换槽/增删/Root 替换持写锁，停机封住新 lease 并无超时等待已有 lease 归零 |
| listener 槽位 | listener/UDP socket 的 pData 指向稳定槽位；槽位拥有 runtime/generation/TLS 表和每个 native listener 的终态引用，显式区分 bound 与 accepting。Accept 持 topology 读锁后再在槽位锁内捕获 runtime/generation；事务持 topology 写锁切完全部槽位，并把监听资源引用逐个精确转移。listener 异常关闭只撤销自己的资源位，槽位在 owner 与全部资源终态后才释放 |
| 连接注册表 | Accept 入表并捕获 registry/generation；HTTP 每请求短持选中脚本（TAKEOVER 延长到 Close），WS 在握手时持有脚本到 Close。Close 先出表再释放引用，安全性由 lease 而非无锁 `iCount` 推断 |
| End 终态桥接 | HTTP/TCP/WS 握手层及 TAKEOVER 的明文/TLS `End` 一律请求 `Close`，避免客户端 FIN 后服务端永久停在 `CLOSE_WAIT` |
| WS 热换 | Accept 只捕获 server generation，upgrade 检查完成后按 Host 选择并 Retain 该代 host/脚本到 Close；活动链与计数由 mutex 保护 |
| TCP/TLS 热换 | 明文与 TLS 可分别绑定 `ip/port`、`ip_tls/port_tls`；有 `xrtNetStreamSetEvents`（仅所属 Worker 线程、不重放遗留缓冲），完成 Accept 后才安装业务事件，握手失败始终走 listener 内部终态 |
| 证书热替换 | 证书链、`tls_ca` 中间证书与 TLS 表作为新 server generation 的一部分完整重建；同端点提交时 listener slot 一次转向新表。selector 把选中 generation cookie 固化到会话，Accept 只接入同一代；identity 由会话 Retain，跨提交握手不会读已释放证书或误接新 runtime |
| 定时器隔离 | timer 同时 Retain 脚本代与服务代；脚本/服务退役立即请求取消，OK/CANCELLED/CLOSED 共用一个终态释放出口 |
| 初始化屏障 | server 本次需激活的全部脚本和 endpoint 先准备；越过 staging 后才执行 `ServiceSwap/ServiceInit`，脚本保持 not-ready，Init 创建的 lifecycle timer 通过 generation 级发布条件等待整个事务发布 |
| 协调与防重入 | 所有 reload API 只向独立 controller 提交名称，不保存可能退役的裸指针；controller 串行构建，latest-wins 合并意图，提交栅栏与 Submit 共用短锁确定线性顺序 |
| VFS 并发快照 | 每个 TCCState 使用唯一 `/xs/script/<state>.c` 动态路径，`mount_memory/open` 在全局锁内取得深复制快照，打开的虚拟 FD 独立持有数据；`add_file` 返回即 unmount。外层 reload 编译与脚本中的嵌套 TCC 可并发，不会覆盖路径、悬空或串读其他候选 |
| server 级事务 | 无论配置文本是否变化，server reload 都重建完整 generation，不再逐 host 发布；同端点兼容变化走稳定 listener 切槽，端点改变走候选 bind，固化字段同端点改变明确拒绝 |
| 配置所有权 | 一个 intent 只解析一次配置；reload-all 的全部新 generation 分别 Retain 同一不可变 `XS_ConfigRevision`，最后一个终态 finalizer 才统一释放 server 字符串、host 锁和 xvalue 树，避免按 server 重复解析/复制形成 O(N²)。根 Custom 在拓扑写锁内替换，`xsConfigRoot` 返回 retained xvalue |
| 运行状态 | server/host 的 `State` 只在候选发布前写入，发布后作为不可变快照读取；失败、覆盖和取消属于 reload ticket 状态，不回写仍在服务的旧 generation |
| 协议边界 | `xsReloadHost*` 不是局部原地换脚本，它与 server reload 共用整代候选/发布/排空流程，因此 HTTP/WS/TCP/UDP 都遵守同一生命周期原则；custom 的裸 xrt 资源不可证明终态，在线重载明确拒绝 |
| intent 与结果 | Submit 返回非零 `reload_id`；状态为 accepted/preparing/succeeded/failed/superseded/cancelled。pending 上限 64，结果保留环 256；环槽内的非终态 ticket 绝不被覆盖 |
| 输入 revision | 每个 host/server/all intent 只解析一份冻结的 xs.json 字节；主 `devfile` 首次读取后在该 intent 内复用并计入 revision 指纹。`dev_inc/dev_lib`、证书和脚本自行读取的外部资源必须来自不可变版本目录；发布器应新建版本目录后原子切换 xs.json，不应就地覆写正在构建的输入 |

### 10.4 停机

优雅停机先关闭 reload admission：pending ticket 置 `cancelled`，未进入 staging 的 active ticket 置 `superseded/cancelled` 并回收候选，已进入 staging 的任务完成发布与收尾。controller 线程退出后，builtin 停 listener、主动 Close 活动连接并退役 generation；随后 **无超时等待**公开 topology lease 与全部网络对象进入终态，再 Stop/Destroy 引擎。custom 保留 TCC 到引擎停止，之后才退役并撤销 owner 引用；最后排空 reaper，确保所有 `ServiceUnit` 和 driver/TCC/配置 revision 终析构完成。任何连接或公开 lease 不终态就继续等待并打印状态，绝不以超时换取 UAF，也不放弃 owner 引用制造永久泄漏。

### 10.5 管理面语义

- `/reload`、`/reload-svr`、`/reload-all` 受理时返回 HTTP `202` 和 `reload_id`；`503` 表示未受理。`202` 不代表已发布。
- `/reload-status/<id>` 返回 ticket 的终态和 revision 指纹；超出有界结果环的旧 ID 返回 `404`。
- 发布系统只能在 `succeeded` 后把该 revision 记为活跃；`failed`、`superseded`、`cancelled` 都不是异常的“队列丢件”，而是有明确终态的协调结果。

## 11. TCC 脚本宿主

### 11.1 已验证事实（PoC，2026-08-29）

- TCC 0.9.28rc（x86_64 Windows）编译 44,199 行 `xrt_decl.h` 声明头：**零错误，~25ms**；
- 完整宿主模型仿真通过：GCC 宿主 + `TCC_OUTPUT_MEMORY` + `tcc_add_symbol` + `tcc_relocate` → TCC 编译脚本调用宿主 xrt 函数，**结构体按值传参 ABI（xstrview）与 xvalue 跨界操作全部正确**，编译+链接 6.9ms；
- 耗时对比现役 `inline_xrt.h`（7,688 行，34–46ms）：新头反而更快，重载延迟无回退。

### 11.2 工程要点

- 脚本侧包含 `inc_xs/xsbase.h` + `inc_xs/xrt_decl.h`（由 xrt `tools/amalgamate.py` 生成，随 xs 版本锁定发布）。
- 符号导入按模块分组宏门控：`XS_IMPORT_CORE / XS_IMPORT_VALUE / XS_IMPORT_JSON / XS_IMPORT_NET / XS_IMPORT_HTTP / XS_IMPORT_WS / XS_IMPORT_CONCURRENCY / ...`，与 xrt `XRT_MODULE_*` 对齐，应用按需开。
- 操作序列：`tcc_new` → 设 include（`include_win/winapi` 先于 `include_win`，再 `include`、`inc_xs`）→ `TCC_OUTPUT_MEMORY` → `tcc_add_symbol`（分组）→ `tcc_add_file` → **`tcc_relocate`** → `tcc_get_symbol`。
- 库路径必须含 `tcc/lib`（relocate 需要 `libtcc1.a`）。
- `xsCreateTCC()` 预置上述路径与符号导入，返回就绪的 TCCState（xadmin 插件系统的地基）。

### 11.3 内置 VFS 与构建目录 res/（单文件交付）

**xs 不附带任何磁盘上的 TCC 环境**。TCC 所需的一切（SDK 头、winapi/linux 头、`libtcc1.a`、`.def` 导入库）在构建期打包进二进制内置 VFS，运行时从虚拟路径读取；脚本源文件由宿主经 xrt fs 读出后 `tcc_vfs_mount_memory` 挂载（入口文件零编码损耗）。

**VFS 布局与来源**（`tools/gen_tcc_resources.py`，构建期执行）：

| 虚拟路径 | 来源 | 说明 |
|---|---|---|
| `/xs/xsbase.h` `/xs/xrt_decl.h` `/xs/libtcc.h` | `src/sdk` + `lib` | SDK 三件套，**单一事实源为源码目录**，脚本永远编译与宿主二进制同版本的契约头 |
| `/tcc/include_win/**` `/tcc/include/**` | `res/tcc/include_win`、`res/tcc/include` | 精简后的 TCC Windows 头（见 11.4） |
| `/tcc/include_linux/**` | `res/tcc/include_linux` | Linux 侧头 |
| `/tcc/lib/**` | `res/tcc/lib` | `libtcc1.a`（relocate 必需）与 9 个 `.def` 导入库 |

- **res/tcc 即 VFS 构建目录**：它是磁盘上唯一的 TCC 环境副本，构建时整体（LZMA，实测 7.3MB → 1.0MB）编进二进制。**新增内置库/头 = 放入 res/tcc → 重新构建**，无运行时安装步骤。
- 宿主 `XS_TccCreate` 的内置 include/sysinclude/lib 路径均以 `/tcc`、`/xs` 开头，运行无需 `release/tcc`；单文件交付由 `test.bat` / `bash test.sh` 在无磁盘 TCC 环境时回归保证。
- LZMA 打包链：`tools/tcc_vfs_lzma_pack.c`（编码，构建期）+ `tcc/LzmaDec.c`（解码，运行期，VFS 内置）。生成文件首行保存全部输入与生成算法的 SHA-256；命中时跳过 268 次压缩和大型 C 文件重写。
- 运行时 TCC 文件 IO 经 `tcc.h` 宏重映射：`open/fopen → tcc_vfs_*`。查找顺序为本次编译的内存快照 → 真实文件（`dev_inc/dev_lib`）→ 内置资源；动态表与虚拟 FD 全部同步，打开后持有独立快照，UTF-8 宽字符后端支撑中文路径。

### 11.4 TCC 环境精简边界（能力保证面）

include_win 按"保证入口头 #include 闭包"精简（`tools/tcc_include_closure.py`，26M → 6.2M，入口缺失即报警）：

- **保证面**：CRT 全家族；windows.h 全链；winsock2/ws2tcpip（网络）；objbase/oleauto/oaidl/msxml2（**COM/Excel 自动化、XML**）；sql/sqlext（**ODBC 数据访问**）；mlang（**多语言代码页**）；wintrust/wincrypt（签名证书）；wininet（HTTP 客户端）；shellapi/shlobj；psapi/tlhelp32（进程）；sddl/aclapi；lm。
- **不保证**：DDK、OpenGL/DirectX、多媒体、GUI 控件、ISAPI、MSI、ADO 类型化头（IDL 重语法 TCC 不可解析——数据访问走 ODBC 或 IDispatch 后期绑定）。
- 能力回归由两个常驻探针脚本守卫（已入 xs.json 与 test.bat）：`crt_probe_main.c`（printf/CreateFile/CoInitialize/WSAStartup 实调）与 `include_probe_main.c`（一次性包含全部保证入口头）。
- TCC 内存模式自动挂 msvcrt 与 kernel32，其余系统库需显式 `tcc_add_library`——`XS_TccCreate` 已注册与保留 `.def` 一一对应的 7 个库（user32/gdi32/shell32/ole32/oleaut32/ws2_32/imm32）。

### 11.5 可选扩展库（编译宏门控）

| 宏 | 库 | 状态 |
|---|---|---|
| `XS_USE_LIBTCC` | libtcc（嵌套编译） | 第一版必选（宿主自身依赖，同时导出） |

可选库接入公式（以 sqlite 为参照）：**源码进 `lib/` → 构建变体编译为独立 .o（规避巨型单进程编译）→ `nm` 实际导出 × 头文件声明 取交集生成 `import_<name>.inc` → 头文件入 VFS `/xs`（LZMA）→ 探针脚本回归**。

扩展的统一登记点为 `tools/extensions.json`，Windows/Linux 入口共用 `tools/build.py`。支持 `sqlite xtp` 等任意已登记组合，参数顺序无关、重复去重、未知名称报错。同一选中列表控制独立对象、VFS 头、TCC 符号和脚本特性宏；后续接库无需增加宿主或平台构建分支。详情见[可选扩展库](/D:/GIT/xserver/docs/可选扩展库.md)。

正式构建的生成头、VFS 资源 C 文件、对象及变体二进制位于 `.build/<platform>/<组合>/`；旧 `src/script/tcc_builtin_resources.c` 快照不再被正式构建覆盖。最终输出默认仍为 release/xs(.exe)，成功链接后才发布。

### 11.6 应用级目录扩展：dev_inc / dev_lib

内置 VFS（11.3）解决"xs 自带什么"；**dev_inc / dev_lib 解决"应用自带什么"**——应用私有 SDK（业务头文件、第三方 `.a`/`.def`）无需进 VFS、无需改 xs 本体，配置两行即可让脚本的 TCC 环境认识它们。

```json
{
    "class": "custom", "name": "my-app",
    "devfile": "script/main.c",
    "dev_inc": "devsdk/inc;vendor/headers",
    "dev_lib": "devsdk/lib"
}
```

规则（与 devlang/devfile 同构，见 §5 配置模型）：

- **host 级**字段直接生效；**服务级**字段折叠进 DefaultHost（host_default 优先覆盖）；
- 分号分隔多目录；相对路径**只**按 appPath 解析（UTF-8 全链路，支持中文目录），绝对路径原样使用，不回落到进程当前工作目录；
- 头目录同时注册 include 与 sysinclude（尖括号/引号包含都命中）；库目录注册 `tcc_add_library_path`；
- **缺失目录静默跳过**（容错部署）；目录为真实磁盘路径，经 VFS 三级查找（内置 → 内存挂载 → 真实文件）的最后一级命中；
- **热重载生效**：每次重编译的 TCC 环境按当前 host 配置注入（`XS_TccCreateForHost`）；
- `xsCreateTCC()` 嵌套编译走基础环境（不含 host 目录）——应用层插件系统需要同一环境时应基于脚本侧的 tcc API 自行补路径。

示例目录 `release/devsdk/`（`inc/dev_extra.h` + `lib/`），探针 `release/script/devinc_probe_main.c`（`#include <dev_extra.h>` 命中并校验值）。典型场景：xadmin 式应用随包携带业务 SDK，脚本直接 include；第三方库放 dev_lib 供 `-l` 链接。

与 11.3/11.5 的分工：

| 层 | 内容 | 变更方式 |
|---|---|---|
| 内置 VFS（res/tcc） | xs 标准环境（TCC 头、libtcc1、def、SDK 三件套） | 改 res → 重新构建 xs |
| 可选扩展库（XS_USE_*） | 全体应用共享的宿主级库（sqlite…） | 加构建变体 → 重新构建 xs |
| **dev_inc / dev_lib** | **单应用私有 SDK** | **改应用目录 + xs.json，xs 不动** |

## 16. 开发规约

### 16.1 文件与路径操作一律用 xrt（强制）

**所有文件与路径操作必须使用 xrt 的 fs / path 模块（`xrtFileReadAll / xrtFileExists / xrtDirExists / xrtPathStat / xrtPath*` 等），禁止使用 C 标准库文件函数（`fopen / fread / fwrite / remove / rename` 等）。**

理由（历史经验）：C 标准库在 Windows 上走 MSVCRT 的 ANSI 代码页（中文系统为 GBK），对中文路径与多编码支持很差，是过去一批路径 BUG 的来源；xrt 的 fs 层统一按 **UTF-8 路径**设计，Windows 后端为宽字符实现（`CreateFileW` + UTF-8↔UTF-16 转换），从根上消除该类问题。

配套约束：

- 传入 xrt 的所有路径字符串必须是 UTF-8 字节序列；
- **Windows 进程入口必须在启动时用宽字符命令行（`GetCommandLineW + CommandLineToArgvW`）重建 UTF-8 argv**，否则用户在中文控制台传给 `xs` 的路径参数在入口就已按 GBK 乱码（已在 main.c 落地）；
- Windows 控制台输出统一 `SetConsoleOutputCP(CP_UTF8)`，配合 UTF-8 日志字符串；
- `tools/` 下的测试辅助程序豁免（仅处理 ASCII 临时路径），但不得进入运行时代码。

### 16.2 其他既定规约

- `XRT_STR_LITERAL` 仅可用于字符串字面量（`sizeof` 求长）；运行时构造的键名/视图必须用 `xrtStrViewN(s, strlen(s))` 一类显式长度版本。
- 结构键（services / hosts / host_default）从配置树摘取必须用 `xrtValueObjectTake`（移交所有权）；`xrtValueObjectRemove` 会销毁子树，只用于已拷贝完的标量键。
- 结构体 ABI 演化纪律见 §4.1；契约头 `xsbase.h` 的任何改动视同版本事件。

## 附录 B：宿主边界与质量检查（2026-10-25）

`XS_SDK_ABI_VERSION=1` 标识当前契约；公开结构布局与枚举数值由 `tools/sdk_abi_x64.json` 固定，原生编译器、普通脚本和嵌套 TCC 应通过同一份 72 项检查。新增字段仍遵守尾追加纪律，改变基线必须经过显式审查。此契约适用于同进程可信 C 脚本；宿主检查覆盖 xs 管理的资源，不为应用直接创建的线程、原生对象或任意内存操作提供隔离。

| API/回调 | 所有权与有效期 | 并发、重入和终态 |
| --- | --- | --- |
| `xsServerFind` / `xsServerRetain` | 返回持有的 server lease；用 `xsServerRelease` 归还 | 查询内部同步；停机封闭新 lease；原有 lease 仍须归还 |
| `xsHostFind` / `xsEnumHosts` | host 借用期由对应 server lease 或宿主回调保护 | 跨回调保存 host 时，保留其 server；配置及内部 Runtime 字段不可修改 |
| `xsEnumServers` | 枚举参数只在回调内借用；保存时先 Retain | 不持拓扑锁调用应用，可再次查询或提交重载 |
| `xsConfigRoot` | 持有的 xvalue；用 `xrtValueRelease` 释放 | 配置快照只读；不把返回值当作可变的进程配置入口 |
| `xsReload*Submit` / `xsReloadQuery` | ID 与结果值可复制；有限结果环过期后 Query 返回 false | Submit/Query 可并发；回调中提交后不得同步等待自身换代 |
| `xsTimerAfter` / `xsTimerCancel` | userData 归应用，须覆盖可能在途的回调 | Cancel 是取消请求，不是 join；退役拒绝新 timer，终态只记账一次 |
| `xsCreateTCC` / `xsDestroyTCC` | 调用方拥有已预设 MEMORY 输出的编译状态 | 直接 compile/relocate，不再次 set_output_type；同一状态由应用串行化，销毁前生成代码已无人执行 |
| HTTP/流/WS/UDP/XRUDP 回调 | 请求、消息视图仅在回调内借用；长期保存原生句柄须按 xrt 契约 Ref | Worker 回调有界，不阻塞等待同 Worker；关闭可能重入，外层保活到返回 |
| `ServiceSwap` / `xsSwapTake` | Swap 导出快照，Take 转移 xvalue 所有权 | Swap 无破坏；Take 仅在新代 Init 使用；发布失败保留旧服务 |
| `ServiceUnit` | 应用释放自行创建的资源及 lease | xs 管理的脚本活动归零后至多一次；应用的裸线程/回调也须自行停止并等待结束 |

返回结构体中的配置字符串、Custom 与 host 数组由持有的 generation 保护；State/Runtime 等宿主可变字段不提供无锁并发读取承诺。`RuntimeLock`、`Generation`、`ConfigOwner` 为宿主内部字段。

### B.1 资源策略

| 边界 | 默认策略 |
| --- | --- |
| 配置文件 / 入口脚本 | 各 16 MiB；磁盘读入和 VFS 解压前检查 |
| 配置预设字符串 / 单条路径 | 65535 / 4095 字节；拒绝内嵌 NUL；dev_inc/dev_lib 逐段按配置目录解析 |
| services / 单服务 hosts | 各最多 4096 项 |
| `connection_limit` | 默认 4096，允许 1..UINT32_MAX；约束单代活动连接（UDP 为在途回调） |
| `ws_message_limit` | 缺省/0 采用锁定 xrt 的有效默认值，xs 累积器与底层流一致 |
| `ws_memory_limit` | 默认 64 MiB，须覆盖单消息上限；约束单代 WS 累积缓冲容量（含保留缓冲）；不足关闭码 1013 |
| 一次 reload 快照 | 配置与不同入口脚本缓存合计最多 64 MiB；输入在协调器执行时冻结 |
| 退役代积压 | 默认 128；新提交在 Swap/Init 前按本次替换/移除数量检查预算；不强制释放旧对象 |
| VFS 常驻内容缓存 | 默认 256 MiB；互斥保护指针发布与记账；不驱逐进程期借用视图 |
| VFS LZMA 临时输入 | 整条读入、单次解码；分配前要求压缩长度小于原文，输出仍受常驻缓存预算约束；最终输出兼作字典，概率表单独分配 |
| 打包递归 / 归档条目 | 最多 128 层 / 100000 项；单文件最多 1 GiB，遍历与读入均校验；偏移采用减法范围检查，短 LZMA 属性区直接拒绝 |

这些是入口和宿主管理对象的预算，不是进程 RSS 上限。应用原生分配、TCC 编译状态、包含头文件及库资源仍遵循各自契约。并存的新旧代分别持有连接和 WS 预算；退役代数量另受提交预算控制。需要调整编译期策略时使用 `--cflag=-DXS_...=...`，定义见 `src/core/limits.h`，实际选项写入旁置构建记录。网络配置的未知应用字段仍留在 Custom。

### B.2 失败与诊断

路径解析、类型/长度转换或预算检查失败均停止当前候选。可识别的内嵌归档损坏时拒绝自动回落目录模式，显式配置或 `--no-vfs` 可用于诊断恢复。解包先校验完整索引，再逐文件校验内容并在锚定目录内临时写入、改名发布；每个文件独立提交，不承诺整包事务。打包和剥包采用临时输出，失败保留原目标。generation 的 quiesce/finalize 日志带 cookie，可与重载目标及结果关联；停机等待 lease 不以超时为由释放仍在使用的对象。

打包工具的输入路径统一使用 xrt 的 UTF-8 文件接口和 64 位大小查询，支持中文及非 BMP 字符的程序、站点和归档路径。目录枚举错误与正常结束分开处理，关闭失败也中止打包；不将已收集的部分目录当作完整站点。单文件上限在分配、CRC 和压缩之前执行，读入后额外检查 EOF 及文件大小，发现缩短、增长或读/关失败则丢弃候选。此检查不能冻结正在原地改写且长度相同的源文件；部署输入仍应保持静止。

归档生产、工具解析与运行时装载按显式长度共用无分配的规范路径校验，条目长度为 1..4096 字节，拒绝 NUL、反斜杠、前后或重复斜杠以及 `.` / `..` 分段。生产端在压缩前检查全部条目，避免发布读取端无法接受的包；查找请求仍按原有规则进行路径归一化。Unicode 和 `.well-known` 等合法点前缀不受影响。

工具与运行时的 LZMA 解码均要求压缩输入精确消费、原始长度精确匹配，并在解码后检查原文 CRC。解码得到正确原文并不足以接受含额外尾字节的压缩区间。现有不带结束标记的 LZMA1 流继续按已知原始长度解码；失败内容不会发布到缓存或当前解包目标。

### B.3 可重复执行的门禁

```sh
python tools/check_quality.py
python tools/check_quality.py --exe .build/quality-20261025/windows/xs.exe
python3 tools/check_quality.py --sanitize --exe .build/quality-20261025/linux/xs
```

第一条运行快照/构建单元检查、自有源码告警检查、原生故障与并发夹具以及 SDK 布局检查。指定二进制时先验证源码与二进制摘要，再运行普通/嵌套 TCC、功能矩阵、资源预算、生命周期、各协议重载、HTTP/TLS、站点 VFS 与归档回归；编入 XRUDP 时追加原生服务检查。每次输出 JSON 报告，默认 `.build/quality-report.json`，可通过 `--report` 隔离多平台结果。报告记录源码、二进制和测试文件摘要，检查期间输入变化则判失败。功能矩阵为每个进程创建独立 release 夹具副本、配置和日志，不写入真实发布目录。

原生夹具覆盖 57 个配置分配失败点、40 轮发布/退役竞争、VFS 首访并发与失败清理，以及 512 个确定性配置变异/截断样本。`--sanitize` 仅对这些原生夹具启用 ASan/UBSan，不对 TCC 动态生成的机器码作自动插桩承诺。告警门禁检查 default/all 和本平台独立编译的 xs 源文件；条件静态助手的 unused-function 有意豁免，第三方告警单独计数。此门禁不代替长时间稳定性演练。

归档原生夹具另以可控文件/目录接口覆盖枚举中途失败、关闭失败、64 位超限、短读、文件增长和 EOF 探测失败；同样纳入 `test_native_boundaries.py` 与 sanitizer 检查。实际二进制回归覆盖 Unicode 路径下的打包、列表、解包、剥包和重打，以及超限稀疏文件提前拒绝。

原生检查使用真实 LZMA 实现，以相同样本调用工具和运行时的解码助手，比较正常无结束标记样本、三种多余尾字节、所有截断前缀和错误原始长度，核对返回结果与释放记账；二进制回归另检查 CRC 自洽的多余输入不能覆盖已有解包目标。

VFS 压缩输入使用受控分配/读取探针核对：短属性区、压缩长度等于或大于原文（含原文 1 KiB、声明 16 MiB 或 UINT32_MAX）均在分配和读取之前拒绝；正常首访只读取一次完整压缩区间，缓存复用不再读取。真实文件夹具另覆盖有/无结束标记流、输入/输出/概率表三处分配失败、短读、尾字节与 CRC 失败；HTTP 读取验证压缩后超过 64 KiB 的内容及缓存复用。

新增样本生成触发了上游 SDK 的 x86 非对齐访问约定（`CpuArch.h` 的 GetUi/SetUi 宏）。`--sanitize` 对样本编码器 `tcc/LzmaEnc.c` 和匹配器 `tcc/LzFind.c` 单独排除 UBSan alignment 检查，保留 ASan 及其余 UBSan；xs 自有代码、真实 LZMA 解码器和读取探针仍使用完整 ASan/UBSan。例外逐源编译，写入 JSON 报告的 `native_sanitizer_exclusions`，不修改锁定的上游文件。

### B.4 持续加固审查

每轮从一个可复现的边界问题开始，连同回归测试和必要契约说明提交；检查范围、验证证据与剩余限制写入更新记录。源代码、候选产物和正式发布保持各自来源记录。

已统一归档生产端与消费端的路径接受条件。VFS 恢复整条输入、单次解码，以匹配站点小文件为主的用途；启动和首次读取都按自有打包器规则检查 LZMA 压缩长度严格小于原文，不把这一规则当作通用 LZMA 格式要求。VFS 解码期间的受管内容内存由缓存与当前输出、整条压缩输入及概率表组成；这不包含归档索引、分配器开销、工具模式整体读取和其他宿主资源，不能视为进程 RSS 上限。

2026-10-26 按用户要求停用持续加固定时任务。重载准备失败时的退役预算、dev_inc/dev_lib 在配置解析与编译器接入之间的路径长度一致性仍只是待核查方向，不代表已经确认的缺陷。供应链快照和 SDK ABI 继续由现有门禁保护。
