# 文档编写约定

## 1. 以当前实现为准

正式文档必须优先以当前代码和当前可运行行为为准。

对外文档统一只使用 `XServer` 这个名字。

不要把内部代号写成：

- 产品名
- 版本名
- 章节名
- 文档标题

如果后续必须引用现有实现文件名或目录名，只允许把它当成“路径说明”，不当成对外术语。

不要把下面这些内容直接写成“已经完全实现”：

- `force` 已具备完整 draining 语义
- 显式生命周期状态机已经完整落地
- 所有旧文档内容都仍然有效

## 2. 设计与现状要分开写

每篇正式文档建议显式区分：

- 当前实现
- 当前限制
- 后续规划

避免把设计草案中的目标语义和当前主线行为混写。

## 3. 第一阶段文档优先级

第一阶段优先写：

- 能直接指导用户运行和配置的内容
- 能直接指导脚本开发的内容
- 能直接指导管理面和排障的内容

第一阶段暂缓深写：

- 尚未行为化的 `force / draining`
- 未来态的显式状态机
- 未实现的兼容层和扩展协议

## 4. 只写当前版本真实支持的内容

正式文档只适配当前版本真实存在的特性。

已经不存在、未实现、或不再对外支持的内容：

- 不进入正式文档正文
- 不进入配置字段表
- 不进入服务类型列表
- 不进入教程和范例
- 不进入“兼容写法”说明

正式文档应直接使用当前版本实际支持的模型和字段，不为旧概念保留篇幅。

## 5. 示例来源

正式文档中的示例优先引用当前仓库已有文件：

- `release/xs.json`
- `release/xs_ws.json`
- `release/xs_wss.json`
- `release/xs_udp.json`
- `release/xs_xtp.json`
- `release/xs_xtps.json`
- `release/xs_custom.json`
- `release` 下的示例脚本目录

## 6. API 文档边界

API 文档优先覆盖：

- 稳定宿主头文件
- 全量兼容宿主头文件
- `__xs/*` 管理接口

如果未来 API 很多，建议按“分组文档”写，不在一个页面里堆完整函数清单。

## 7. 迁移方式

旧文档不要直接覆盖式重写。

建议流程：

1. 在新目录写新文档
2. 在 `spec/progress.md` 标记状态
3. 新文档稳定后，再归档旧文档或在旧文档头部加迁移说明

## 8. 文件命名

正式文档文件名必须使用英文命名。

建议规则：

- 小写英文
- 连字符分词
- 避免缩写堆叠
- 文件基名在中英文版本之间保持一致

示例：

- `configuration.md`
- `configuration.en.md`
- `script-host.md`
- `script-host.en.md`

不建议：

- `配置说明.md`
- `script_host.md`
- `ScriptHost.md`

## 9. 中英文双份策略

每篇正式文档固定保留两份：

- `xxx.md`：中文版本
- `xxx.en.md`：英文版本

当前工作流程必须是：

1. 先写中文版本
2. 由你审阅中文版本
3. 中文确认无误后，再翻译英文版本

在中文未确认前：

- 不提前写英文正文
- 不提前做英文润色
- 只在 `spec/progress.md` 中预留英文文件和状态

## 10. 进度追踪方式

`spec/progress.md` 应按“文档基名”追踪，而不是把中英文当成两个完全独立主题。

建议字段：

- 文档基名
- 中文文件
- 英文文件
- 中文状态
- 英文状态
- 优先级
- 说明
