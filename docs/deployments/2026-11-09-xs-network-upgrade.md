# 线上 XS 更新与随机连接重置复测

2026-11-09，北京时间 11:00 完成程序切换；本轮最后核对时间 11:04:28。

**结果：升级并重启后，本轮未再复现随机连接重置和 TLS 非正常结束。**
生产流量仍使用原配置、原站点、原 nginx 入口；本次只替换 XS 程序及其构建记录。
这是一轮短期复测，不能据此认定长时间运行问题已被永久消除，也不能将改善归因到某一个 XRT 修复。

## 升级前证据

- 不仅公网 HTTPS 出错，直接访问服务器回环地址的 HTTP 80 和 XS TLS 8440 也会重置连接。
- 部分连接在尚未发送 HTTP 请求头时就被重置，说明这些失败发生在站点路由之前。
- 首批 192 次无请求数据连接出现 15 次重置，失败序号模 64 为 `7、13、17、22、30`，每个位置连续三轮完全重复。线上 XS 默认有 64 个网络工作线程，源码按轮询分配新连接；该规律强烈指向工作线程分配后持有的异常状态，尚未定位到具体拒绝分支。
- 后续两批相同类型的测试中，80 端口为 **65/192** 次重置，8440 端口为 **66/192** 次重置。不同批次的异常槽位数量已有变化，不能认定始终只有 5 个线程异常。
- 测试区间监听队列溢出、监听丢弃、内核 TCP 内存压力计数没有增长，服务器可用内存充足。
- 用旧版同一二进制启动的小型纯静态控制监听，在 1、8、64 个工作线程及 TLS/SNI 测试中没有复现。旧程序长期运行状态与新进程之间存在重要差异。

`TLS transport ended without close_notify` 表示 TLS 会话遇到了未通过关闭通知正常结束的底层连接。它是本轮连接中断的表现；单靠这条消息不能判断是哪一个站点、哪一层代码主动关闭，也不能判断某次下载的 HTTP 正文是否已完整接收。

## 结论与后续判断

目前确认的是：旧线上进程的异常发生在共享连接接入路径，新版进程在本轮相同连接测试中恢复正常。

升级和重启同时发生，本轮没有在生产环境单独重启旧二进制进行对照。因此仍不能区分具体版本修复与重启清除累积状态的贡献。若长时间运行后再次出现，应优先记录每个 worker 的接纳、投递失败、流注册失败及运行时换代状态，再定位触发条件；不应把自动重试成功当成根因已经消除。
