# 可组合的扩展库构建

Windows 与 Linux 共用 `tools/build.py`，`build.bat` / `build.sh` 只转发参数。库清单的唯一登记点为 `tools/extensions.json`。构建与生成工具仅使用 Python 标准库，运行时仍是单个 C 可执行文件。

## 使用

| 构建参数 | 内置的可选库 | 宿主及脚本宏 |
|---|---|---|
| 不传参数 | 无 | 所有可选宏均未定义 |
| `sqlite` | SQLite | `XS_USE_SQLITE=1` |
| `xtp` | XTP2 | `XS_USE_XTP2=1` |
| `xllm` | xllm（LLM 调用核心库） | `XS_USE_XLLM=1` |
| `xllm-session` | xllm 会话治理层 | `XS_USE_XLLM_SESSION=1` |
| `xmail` | xmail（邮件 MIME 基础库） | `XS_USE_XMAIL=1` |
| `xsmtp` | SMTP 客户端（自动携带 xmail） | `XS_USE_XMAIL=1` + `XS_USE_XSMTP=1` |
| `xpop3` | POP3 客户端（自动携带 xmail） | `XS_USE_XMAIL=1` + `XS_USE_XPOP3=1` |
| `ximap` | IMAP 客户端（自动携带 xmail） | `XS_USE_XMAIL=1` + `XS_USE_XIMAP=1` |
| `sqlite xtp xllm` | 三个独立库 | 对应三个宏 |
| `xsmtp xpop3 ximap` | 邮件全家（xmail 只编译一次） | 四个邮件宏均定义 |
| `md4c` | md4c（Markdown 解析 + HTML 渲染） | `XS_USE_MD4C=1` |
| `xacme` | xacme（ACME/RFC 8555 证书签发客户端，五家 DNS provider） | `XS_USE_XACME=1` + 特性宏组 |
| `qrcodegen` | qrcodegen + PNG 输出（QR 码生成） | `XS_USE_QRCODEGEN=1` |
| `xjwt` | xjwt（JWT/JWS 签发验证 + JWKS） | `XS_USE_XJWT=1` |
| `xoauth2` | xoauth2（OAuth2 客户端 + OIDC 辅助） | `XS_USE_XOAUTH2=1` |
| `all` | **全部可选库**（含依赖自动展开） | 全部可选宏均定义 |

```bat
build.bat sqlite xtp
build.bat xtp sqlite xtp
build.bat xllm
build.bat sqlite xtp xllm
build.bat xsmtp
build.bat xsmtp xpop3 ximap
build.bat all
build.bat --list-extensions
build.bat sqlite xtp --dry-run
```

前两条选择相同的库组合。Linux 将入口替换为 `bash build.sh`。名字不区分大小写，重复参数去重，按清单顺序生成同一个构建变体；未知名字在编译和写入构建文件之前报错，退出码为 2。

**全选（`all`）**：`all` 是保留参数名（大小写不敏感），等价于展开清单中的全部可选库；可与显式名混用（结果一致），产物目录名如实列出全部库名。发布包的"全功能版"即 `build.bat all` / `bash build.sh all`。

**依赖自动展开（`requires`）**：xsmtp / xpop3 / ximap 在清单里声明 `"requires": ["xmail"]`——选中任一协议库即自动携带 xmail（组合构建时 xmail 源码与符号只编译/注册一次，目录名如实展开，如 `.build/windows/xmail+xsmtp/`）。展开在选库阶段完成并做环检测；清单里出现未知依赖、自引用或循环依赖都会在构建前报错。

默认输出 `release/xs.exe`（Windows）或 `release/xs`（Linux）。可选工具参数：

- `--output PATH`：设置产物路径；相对路径基于调用者当前目录。
- `--build-dir PATH`：设置中间文件根目录，下面仍按平台/组合分目录。
- `--cc PATH`：指定 C 编译器可执行文件，默认 gcc。
- `--dry-run`：只输出命令，不创建构建文件、不调用编译器。
- `--list-extensions`：显示登记的可选库与对应宏。

无参数不会隐含启用任何可选库。xrt、libtcc、VFS 与 LZMA 解码器属于固定基础能力，不需要传库名。本入口支持原生 Windows/Linux 构建，不将 `--cc` 视为完整的交叉编译配置。

## 同步控制的四个部分

同一份选中列表用于：

1. 将库源码编译成独立对象，只链接选中的对象和系统依赖。
2. 只将选中的库头文件打包到 VFS 的 `/xs`。
3. 生成宿主头文件声明和符号表，在每个 TCC 环境导入对应函数。
4. 向宿主编译器和 TCC 脚本定义对应的 `XS_USE_*` 宏。

脚本可直接调用：

```c
#include <xsbase.h>

#ifdef XS_USE_SQLITE
#include <sqlite3.h>
#endif

#ifdef XS_USE_XTP2
#include <xtp2.h>
#endif

#ifdef XS_USE_XLLM
#include <xllm.h>
#endif
```

使用宿主内置 XTP2 时不要再定义 `XTP2_IMPLEMENTATION`。它只在编译 `lib/xtp2.h` 的原生实现单元时定义；其他单元只读取声明。XTP2 仍不创建 TCP/TLS 连接，不新增 xs 协议类，也不替应用管理会话。

xllm（vendored 于 `lib/xllm/`，来源 xrt 仓库 extlibs，v3.0.0 核心层）是 LLM 服务调用的客户端库：请求/消息/多模态 part 构造、Chat Completions / OpenAI Responses / Anthropic Messages 三种线上方言、SSE 流解码、重试与取消。它的 xrt 依赖（网络/TLS/JSON/取消等）由宿主内建的全量 xrt 提供，脚本无需也不应再链接任何 xrt 实现；xllm 句柄（`xnetengine*`、`xfuture*`）在头文件中是不透明前置声明，直接使用宿主创建的引擎即可。会话治理（xllm-session）与长期记忆（xllm-memory）分层未纳入本变体。

xmail 系列（vendored 于 `lib/{xmail,xsmtp,xpop3,ximap}/`，来源 xrt@6bbb256e 拆分）是邮件四件套：**xmail** 为 MIME 基础层（编解码/字符集/地址/日期/参数/多部分/消息树/构造器/线上格式/传输，89 符号），**xsmtp/xpop3/ximap** 为三个协议客户端（43/47/101 符号），经 `requires` 自动携带 xmail，共享其传输与 SASL 内部实现。四个库的公开头不是自包含的（引 `<xrt/*.h>` 模块头），由 `lib/xmail/shim/` 垫片层把 xrt 核心模块头映射到 `lib/xrt_decl.h` 的无门控全量声明（宿主经 `-I`、脚本经 VFS `/xs` 同一份解析）；`shim/xrt/promote.h` 按 lib/xrt.h 的语义把 `XRT_MODULE_*` 持久提升为 `XRT_FEATURE_*`（xrt_decl.h 自身只临时启用后还原）。宿主与 TCC 脚本环境都会同时获得 `XS_USE_*` 与 `X<LIB>_MODULE_ALL` 两级宏。上游的 single 单头（把内嵌 xrt 实现圈进同一个实现宏，与宿主 main.c 的全量 xrt 冲突）不适用也不收录，详见各库 `UPSTREAM.txt`。

md4c（vendored 于 `lib/md4c/`，来源 github.com/mity/md4c，MIT 许可）是符合 CommonMark 的 Markdown 解析器：`md_parse` 提供 SAX 风格的块/span 事件流回调，`md_html` 在其上实现 HTML 渲染（表格、删除线、任务列表等经 flag 开启）。头自包含、无特性宏、无链接依赖，导入符号仅 `md_parse` 与 `md_html` 两个。使用注意：回调函数指针无空保护——直接调 `md_parse` 必须提供完整回调结构，或改用自带完整回调的 `md_html`；定义 `_UNICODE` 时 `MD_CHAR` 为宽字符，TCC 脚本默认窄字符。

xacme（vendored 于 `lib/xacme/`，来源 xrt@791f91e6）是 ACME（RFC 8555）证书签发客户端：账户/订单/dns-01 挑战/证书获取/吊销，自带同步 HTTPS 传输（xrt http1+TLS，传输级重试 3 次退避）与 UDP TXT 传播探测，仅依赖 xrt 核心、不依赖任何其它 extlib。公开面 31 个 `xrtAcme*`：不透明客户端 API（`xrtAcmeClientCreate/Issue/IssueEx/Revoke/Rollover/Deactivate/IssueStored`，含 Issue 总预算与备用证书链）、一站式申领（`xrtAcmeObtain`，账户按 CA 持久化复用）、grant 存储扩展；另有 8 个签发入口 `xacmeClient*`（VFS 以 `xacme/` 子路径收录 flow/csr/http/jose/dnscommon/sigv4 头）。内建五家 DNS provider（阿里云/Cloudflare/腾讯云 DNSPod/AWS Route53/华为云，共享 dnscommon 层与 sigv4 签名骨架）；宿主可自填 `xacmednsprovider` 结构接入任意厂商。证书密钥可选 ES256/RSA（PKCS#8/PKCS#1 双读）；key.pem/account.pem 落盘 POSIX 0600。特性宏为多宏组（XACME_MODULE_* + XRT_MODULE_ALL），经注册表 `feature_macro` 列表统一注入宿主与脚本。

另外：xrt 核心模块头垫片层已从 xmail 私有提升为 SDK 常驻（`lib/xrtshim/`，VFS 固定打包 `/xs/xrt/*.h` 与 `/xs/xrt.h`）——任何引 `<xrt/…>` 模块头的扩展都能共享，不再与 xmail 条目耦合。

脚本侧除了 `#ifdef XS_USE_<名>`（编译期探测），还可以在运行期调用契约函数 `xsExtensionEnabled("名")`：按注册表名（= build 参数名，与启动横幅一致）查询本变体是否编入某扩展，大小写不敏感，`requires` 展开的依赖项同样可见，未知名/空串/NULL 恒返回 false 且不设置错误。名表来自构建期生成的 `g_XS_ExtensionNames`。

枚举 API 与探测配对使用：`xsExtensionCount()` 返回本变体编入的扩展数量，`xsExtensionName(i)` 按注册表顺序取名字（= build 参数名，与启动横幅/--version 同一数据源；返回静态常量的借用指针，越界返回 NULL）。default 变体下 count 为 0。枚举出的名字喂给 `xsExtensionEnabled` 必为 true。

qrcodegen（vendored 于 `lib/qrcodegen/`，来源 github.com/nayuki/QR-Code-generator，MIT）是 QR 码生成器：9 个上游函数（编码三入口 Text/Binary/Segments、数字/字母数字模式探测、缓冲计算、模块矩阵读取 getSize/getModule）加 xserver 侧 PNG 输出层 `qrcodegen_png`（qrpng.c/h，1-bit 灰度 PNG，IDAT 经 xrt 的 XDEFLATE_ZLIB 流式压缩，CRC32 本地实现）。全库 1,412 行、零动态分配（上游）、返回的 PNG 缓冲以 xrtFree 释放。典型用途：2FA provisioning（otpauth:// URI 转 QR）、支付/收款码动态生成、API 端点 `GET /qr?text=...`、邮件内嵌二维码（配合 xsmtp）。注意 qrcodegen_Ecc 枚举与 qrcodegen_Mode 枚举是 C 命名风格（非全大写宏）。

xjwt（vendored 于 lib/xjwt/，源自 xrt extlibs，MIT）是 JWT (RFC 7519) / JWS (RFC 7515) 签发与验证库：HS256/384/512、RS256/384/512（PKCS#8/PKCS#1 双封装私钥）、ES256（SEC1/PKCS#8，签名按 RFC 7518 §3.4 DER 编码，与 OpenSSL 双向互认）三族算法 + JWKS (RFC 7517) 公钥集选钥验证。公开 API 24 函数四档渐进：一步式（xjwtHs256 等七规格，不注入 iss/aud）、config 式（xjwtSign 注入 iss/aud/sub/jti/exp/iat 与 header kid）、JWKS（xjwtVerifyJwks 按 kid 严格匹配选钥）、公钥缓存（xjwtKeyParse/xjwtVerifyKey 高频验证免 PEM 重复解析）。claims 以 xvalue* 承载（脚本层零桥接，配合 import_xrt 的 xrtValue* 家族使用）；错误码经 xjwtLastError() 一行读取（EXPIRED/NOT_YET/ISSUER/AUDIENCE/SIGNATURE/KEY_NOT_FOUND 等，可直接映射 HTTP 401 语义或驱动 JWKS 轮换重试）；xjwtClaimString() 安全截断提取字符串 claim。安全基线：exp/nbf 非整数拒绝、aud 支持字符串与数组、alg=none 与算法混淆三路径拒绝、iss/aud/HS 常时比较、kid 严格匹配。典型用途：Web API 认证中间件（Bearer 令牌签发/校验）、第三方 IdP id_token 验证（JWKS + 密钥轮换重试）、微服务间服务令牌。

xoauth2（vendored 于 lib/xoauth2/，源自 xrt extlibs，MIT）是 OAuth 2.0 (RFC 6749) 客户端扩展库：授权码流程 + PKCE (RFC 7636) + token 刷新 + 五家 provider 预设（GitHub/Google/WeChat/Microsoft/Custom，Microsoft 端点与 issuer 按 tenant 动态生成）+ OIDC 辅助（nonce 一次性焚毁、HttpGet 拉 JWKS、GetUserInfo Bearer + 对象守卫）。公开 API 25 函数，传输经 xoauth2httpproc 回调注入（测试 mock 可离线驱动全流程），附 xrt net/tls/http1 便捷实现 xoauth2HttpXrt（http/https 双 scheme、IPv6 字面量、系统或指定 CA、响应体 1MB 上限），并提供堆版 Create/Destroy（opaque 场景/脚本层正路）。错误码经 xoauth2LastError() 一行读取，四级分级 NETWORK/ENDPOINT/DENIED/RESPONSE 可直接映射 HTTP 语义。安全基线：state/nonce 常时比较 + 一次性焚毁、verifier 用后焚毁、请求体全字段 form 编码、Basic 头 RFC 6749 §2.3.1、token 敏感字段释放前清零、expires_in 非整数拒绝。**与 xjwt 为数据耦合：两库零链接依赖（无 requires），OIDC 登录组合在应用/脚本层 8 行胶水完成**（HttpGet JWKS → xjwtJwksParse → xjwtVerifyJwks → nonce 消费 → userinfo，见 lib/xoauth2/examples/ 与组合回归测试）。典型用途：GitHub/Google/微信第三方登录、OIDC id_token 验签后签发本地会话（配合 xjwt）。

未启用的库没有内置头文件和宿主导入符号；这不是沙盒，应用仍可自行通过 dev_inc/dev_lib 等方式提供自己的库。`xsCreateTCC()` 使用同一基础初始化入口，因此嵌套 TCC 也得到一致的可选库和宏。

## 构建产物隔离

```text
.build/
  windows/
    default/
    sqlite/
    xtp/
    xllm/
    sqlite+xtp/
    sqlite+xllm/
    sqlite+xtp+xllm/
  linux/
    default/
    sqlite/
    xtp/
    xllm/
    sqlite+xtp/
    sqlite+xllm/
    sqlite+xtp+xllm/
```

每个变体包含压缩工具、生成的 `xs_build_extensions.h`、`tcc_builtin_resources.c`、对象文件与该变体的可执行文件。每次完整重编译本变体，不会通过文件存在与否猜测是否应链接其他库，也不会复用另一变体的对象文件。

VFS 内容哈希命中时跳过重复压缩。压缩临时文件由每次生成调用独占，不再共用仓库根的 build_tmp_pack_in/out。正式构建不覆盖工作区的 `src/script/tcc_builtin_resources.c` 旧生成快照。

链接成功后才通过临时文件替换指定输出；编译、链接、复制失败不会替换原输出。Windows 下若运行中的程序锁住输出文件，构建会明确报错，不会终止用户进程；可用 `--output` 选择其他位置。不同变体可并行构建，但不要让多个构建同时使用同一变体目录或同一发布路径。

## 增加后续库

例如要提供一个名为 `mylib` 的 C 扩展：

1. 放置库源码与公开头文件，例如 `lib/mylib.c`、`lib/mylib.h`。
2. 新建 `src/script/import_mylib.inc`，列出确实能链接且向脚本开放的符号：

```c
XS_MYLIB_SYMBOL(mylib_create)
XS_MYLIB_SYMBOL(mylib_process)
XS_MYLIB_SYMBOL(mylib_destroy)
```

3. 在扩展清单中增加一项：

```json
{
  "mylib": {
    "macro": "XS_USE_MYLIB",
    "headers": {"mylib.h": "lib/mylib.h"},
    "sources": [{"path": "lib/mylib.c"}],
    "symbols": "src/script/import_mylib.inc",
    "symbol_macro": "XS_MYLIB_SYMBOL"
  }
}
```

这是需要合并到现有清单的示例，不是替换其他库。随后即可执行 `build.bat sqlite xtp mylib` / `bash build.sh sqlite xtp mylib`；不需要修改构建驱动或 tcc_host.h。

清单可列出多个头文件、多个 C 源文件。源码项还支持 `defines`、`flags` 数组，例如单头库使用：

```json
{"path": "lib/mylib.h", "defines": ["MYLIB_IMPLEMENTATION"]}
```

实现宏只作用于该源码对象。平台系统依赖可在库条目添加 `"link_flags": {"windows": ["-lws2_32"], "linux": ["-lm"]}`。所有库源码必须是仓库内存在的文件；相对路径基于仓库根目录。虚拟头文件名不能互相冲突或覆盖核心 SDK 头。

符号清单应以实际对象导出和头文件声明为依据。平台专用 API 在清单中使用预处理条件保护；SQLite 的三个 win32_set_directory 符号只在 Windows 导入。inline helper 不需要导入。当前 SQLite 暴露 272 个 Windows 符号、269 个 Linux 符号；XTP2 暴露全部 13 个外部函数；xllm 暴露核心层全部 53 个外部函数（`tools/test_extensions.py` 对三个库均有头文件-清单一致性断言）。

## 验证

```sh
python tools/test_extensions.py
python tools/test_extensions_runtime.py --exe release/xs.exe sqlite xtp xllm
```

Linux 使用 python3 与对应的 xs 路径。运行时探针的参数必须与目标二进制匹配；它检查脚本特性宏、SQLite 内存数据库操作、全部 XTP2 外部 API、xllm 离线调用（错误/finish 枚举名、token 估算、请求生命周期）、嵌套 TCC 调用，以及未选中库的头文件/符号缺失。

探针只创建临时脚本、配置和短生命周期进程，不创建监听、不操作已有 xs 实例。它在自己的 ServiceInit 中主动 exit，适合作为构建导入验证，不替代网络层、优雅停机或长期稳定性测试。
